The seven stages

  1. Connect — in the target, allow inbound changes from the source. One-directional.
  2. Create — outbound change set, versioned name, real description.
  3. Add — one component type at a time. Profiles last.
  4. Dependencies — add what you need, exclude what would overwrite, re-run after changes.
  5. Manual steps — two written lists: before and after.
  6. Upload and validate — upload freezes the set. Always validate.
  7. Deploy and verify — pre-steps, deploy, post-steps, smoke test as a real user, log it.

Golden rules

  1. Change sets add and update only. Never delete.
  2. The receiving org authorises inbound.
  3. Uploading freezes the set — clone to change it.
  4. Add profiles last. They carry only settings for components in the same set.
  5. Validate first, every time, into Production.
  6. All-or-nothing — one failure means nothing deployed.
  7. There is no undo. Prepare the reversal before you need it.
  8. Test as a real user, not as an admin.

Never travels in a change set

  • Data of any kind — including custom setting values
  • Deletions of anything
  • Permission set assignments to users
  • Record type assignment to profiles
  • Standard picklist values (usually)
  • Flow activation (usually) — old version stays active
  • Queue membership; assignment rule activation
  • Integration secrets, named credentials, scheduled jobs
  • Report / dashboard / template folders you forgot to include
  • Translations for new picklist values

Test levels

  • Default — no tests in sandboxes; local tests run automatically in Production if Apex is present
  • Run local tests — the standard choice for Production
  • Run all tests — includes managed packages. Slow; only when implicated
  • Run specified tests — targeted, must still meet coverage rules

Production needs ≥75% Apex coverage and some coverage on every trigger. Coverage failures need developer work — find them days early, not on release night.

Quick Deploy

A successful validation that ran tests unlocks Quick Deploy on the Deployment Status page — applies validated components without re-running tests.

It expires (commonly cited as 96 hours for change sets; CLI validations are documented at 10 days) and disappears if metadata changes or another deployment runs. Then re-validate — nothing is wrong.

Validate in business hours when help is available. Deploy in the evening when the blast radius is smallest.

Go / no-go

  • UAT signed off, by name
  • Validated against the target
  • Manual steps written — before and after
  • Rollback plan decided
  • Window agreed, inside policy
  • Named approver said go
  • Someone who understands the change is around afterwards

Deployed fine, nobody sees it

The most common outcome of a "successful" deployment. Check in this order:

  1. Field-level security / profile not in the set
  2. Field not on the layout the user sees
  3. Permission set deployed but not assigned
  4. Record type not assigned to the profile
  5. Flow arrived inactive
  6. Custom setting empty in the target

When a change set is the wrong tool

  • You need to delete metadata
  • You're renaming an API name
  • The release is very large
  • The same package goes to unrelated orgs
  • You need version history or an audit trail
  • You need a guaranteed rollback
Escalate rather than forcing it. These want a source-driven tool.

Naming convention

YYYY-MM-DD_TICKET_description_vN

2026-08-12_CRM-4412_case-routing_v1

Version matters because uploads freeze and every fix is a clone.

If it goes wrong

Failed: nothing applied. Fix in source, clone, re-validate. Annoying, not dangerous.

Succeeded but broken: deactivate the offending automation first, then work the prepared reversal.
