Deployment Quick reference handbook

Before you start

Change sets are a way to move metadata between Salesforce orgs. Change sets are good at moving a lot of standard configuration changes but are not always the right tool for every job. Here are some things to understand before you use a change set for your deployment.

Five points about change sets

  • Change sets add and update. They never delete. Removing a field, layout, or rule from Production is a manual job, done manually in Production, after the deployment.
  • They only work between related orgs — this is typically a Production org and the sandboxes refreshed from it. Connections must be enabled between these orgs.
  • Once you 'upload', the change set is frozen. You cannot add a forgotten component. You will need to clone the frozen change set, add the component, and upload again — it is a good idea to use version numbers in the change set name.
  • A deployment is all-or-nothing. If one component fails to deploy the entire change set package is not applied. This is a feature.
  • There is no undo. A "rollback" means a reverse change set you built in advance, or manual unpicking. Have a plan before you deploy.

When a change set is the wrong tool

Recognising these early can save wasted time and frustration:

  • You need to delete something. Change sets can't. Manual removal, or a destructive-changes deployment through the Metadata API.
  • You're renaming an API name. Deploys as a new component and leaves the old one behind.
  • The release is very large. Hundreds of components are unmanageable to assemble and very difficult to review by hand. Break it into smaller chunks.
  • The same package goes to several unrelated orgs. One org 'family', one target per upload.
  • You need detailed version history or an audit trail. A change set records what moved. Included components will show a 'last modified by' until the next update.
  • An emergency fix that must be revertible on demand.
What to do instead

Those cases want a source-driven tool — Salesforce CLI with version control, or a product like Gearset or Copado. It is worth considering when the change set is the wrong shape for the job.

The seven stages

The typical stages required to deploy a change set.

01

Connect the environments

Done once per pair of orgs. A refreshed sandbox is effectively a new org, so it needs doing again.

Setup → Quick Find → Deployment Settings
Receiving org must grant permission

The receiving org grants permission, not the sending org. Authorisation is one-directional. Sending Dev → UAT means logging into UAT and allowing inbound changes from Dev.

Steps — Dev to UAT

If this stage misbehaves

  • The target isn't in the dropdown when I upload. Inbound changes aren't authorised in the target. Go tick the box there.
  • The org isn't in Deployment Settings at all. It isn't a related org — change sets won't work.
  • It worked last month, not now. The target sandbox was refreshed. Re-authorise.
02

Create the outbound change set

In the source org. Naming and description are not admin overhead — they are the context the person deploying will have.

Setup → Quick Find → Outbound Change Sets → New

Name it so the next person understands it

Uploaded change sets freeze and get cloned, so a version number saves you from three change sets called "Case Changes":

YYYY-MM-DD_TICKET_short-description_vN

2026-08-12_CRM-4412_case-routing_v1
2026-08-12_CRM-4412_case-routing_v2

Checklist

Why the description matters

A description saying "changes" is how deployments get deployed by someone who has no idea what they're deploying.

03

Add components

The picker shows one component type at a time. It's repetitive and there's no bulk shortcut, so work from a written list rather than memory.

Open the change set → Change Set Components → Add
Order matters for one thing

Add profiles and permission sets last, after everything else is in. A profile in a change set carries only the settings relating to components in that same change set. Add it first and you export an almost-empty profile.

Method

Commonly forgotten

  • The page layout a new field needs in order to be visible
  • Record types, when a layout assignment depends on them
  • The folder for a new report, dashboard, or email template
  • The object itself, when the field is on a brand-new object
  • Tabs and app assignments for a new object
  • Custom labels referenced by a flow or formula
04

Check dependencies

Salesforce inspects your components and lists other metadata they reference. It catches a large share of failures — treat it as a helpful assistant, not an authority.

Open the change set → View/Add Dependencies
Select All is not free

Selecting everything is how a small field change quietly overwrites a page layout somebody else spent a week on.

What dependency checking will not catch

  • Hard-coded IDs in formulas, flows, templates, or default values. IDs differ between orgs, so these break silently after a successful deployment.
  • Features not enabled in the target org.
  • Data — custom setting values, reference records, anything a user typed.
  • Folders for reports, dashboards, and templates.
  • Users, queues, or public groups referenced by rules, dashboards, or record owners.
  • Record-type-specific picklist availability.
  • Whether the change actually works for a real user.
05

Write down the manual steps

The stage people skip, and the stage that causes the bad Monday. Some things simply don't travel in a change set. If they aren't written down, they don't happen.

Keep two lists

What must happen before the deployment, and what must happen after. Both belong somewhere the deployer will actually see — the change set description should point at them.

Picklist values and record types

  • New values on a custom picklist field travel with the field.
  • Values on standard picklist fields (Case Status, Opportunity Stage, Lead Source) frequently need adding by hand.
  • Record type availability is the classic trap: the value deploys, but which record types it's available for often needs setting manually. Check every record type on the object, not just the one you worked in.
  • Assigning record types to profiles is manual. New record type, nobody can use it — that's usually why.
  • Translations for new values don't come along.

Profiles, permission sets, field-level security

  • A profile carries only the settings for components in the same change set. Never a full copy.
  • Deploying a profile never removes permissions in the target. It only adds and updates.
  • Permission sets deploy in full — assigning them to users is manual, every time.
  • Field-level security arrives only for fields in the set, only for profiles in the set. Verify per profile.
Test as a user, not an admin

After deploying, log in as a real user on each affected profile. Admins see everything, which makes them the worst possible testers of a visibility change.

Flows, queues, and rules

  • A flow usually arrives inactive. It deploys active only if the org allows it (Setup → Process Automation Settings) and coverage requirements are met. Assume inactive and check.
  • Activating the new version doesn't always deactivate the old one. Confirm you don't have two flows racing on the same trigger.
  • Queues deploy; membership — users and public groups — is usually manual.
  • Assignment and escalation rules: the rule and entries deploy, activation is manual, one active rule per object, and entry order changes behaviour.
  • Lightning record page activation and assignment normally needs redoing.

Custom settings vs custom metadata

Worth learning once, because it explains deployments that succeed and do nothing:

DefinitionThe values
Custom settingDeploysDoes not deploy — it's data. Enter or load it manually.
Custom metadata typeDeploysAdd as components deliberately, then verify they arrived.
Reference data in objectsn/aNever deploys — needs a data load.

The rest of the usual suspects

  • Feature enablement in the target — a component depending on a switched-off feature fails to deploy at all.
  • Folders for reports, dashboards, and email templates, plus their sharing.
  • A dashboard's running user must exist in the target.
  • Scheduled jobs and scheduled Apex need re-scheduling.
  • Integration secrets — connected apps, named credentials — never travel.
  • Public group membership and sharing rule recalculation.

Checklist

06

Upload and validate

Upload from the source, then dry-run it in the target before anything real happens.

Source: Outbound Change Sets → Upload · Target: Inbound Change Sets
Upload is a one-way door

The moment you upload, the change set is frozen. Need a change? Clone, adjust, bump the version, upload again.

In the target org the change set appears under Change Sets Awaiting Deployment, with three options: Validate, Deploy, Delete.

Always validate first

Validate runs the entire deployment as a dry run and changes nothing. Same engine, same errors, no consequences. There is no good reason to skip it for Production. It buys you a complete error list while fixing is still cheap — and, if you ran tests, the option to Quick Deploy later.

Test levels

OptionWhat it runsWhen
DefaultNo tests in sandboxes. In Production, local tests run automatically if the set contains Apex.Config-only changes to a sandbox.
Run local testsEvery test in your org, excluding managed packages.The standard choice for Production.
Run all testsEverything, managed packages included.When a managed package is genuinely implicated. Slow.
Run specified testsOnly the classes you name.Targeted checks — must still satisfy coverage rules.
Coverage stops Production deployments dead

Production requires at least 75% Apex coverage overall, and every trigger needs some coverage. This is the most common hard stop, it needs developer work, and it cannot be solved on release night. Validate early enough that finding out is inconvenient rather than catastrophic.

What validation does to the org

While validation or deployment runs, Salesforce briefly locks Setup metadata so nobody changes config mid-check. Users keep working with data normally. Tell your admins not to touch config during the window; you don't need to tell users anything.

Quick Deploy

A successful validation that ran tests unlocks Quick Deploy on the Deployment Status page. It applies the already-validated components without re-running the test suite, turning an hours-long Production deployment into minutes.

  • It expires. The figure commonly cited for change sets is 96 hours (4 days); Salesforce CLI validations are documented as valid for 10 days. Don't build a plan on the exact number — validate close to release and confirm the button is still there before promising anyone a fast deployment.
  • It disappears if relevant metadata changes, or if another deployment runs in between. Then you re-validate. That's normal, not a fault.
The pattern that works

Validate during business hours, when colleagues are around to help fix errors. Quick Deploy in the evening, when the blast radius is smallest.

Checklist

07

Deploy and verify

Deployment success means the metadata was accepted. It does not mean the change works.

Target: Inbound Change Sets → Deploy · Monitor: Setup → Deployment Status

Order of operations

It runs server-side

Closing your laptop doesn't stop a deployment. Don't start a second one — the org runs one at a time.

If it goes wrong

  • Failed deployment: nothing was applied. Read the errors, fix in the source, clone, bump the version, re-validate. Annoying, not dangerous.
  • Succeeded but broken: the real risk. Deactivate the offending automation first — fastest way to stop harm — then work through your prepared reversal.
  • Rollback: no undo exists. Your options are the reverse change set you built in advance, or manual reversal from your notes. Manual reversal without notes, under pressure, is how a small incident becomes a long one.
Twenty minutes well spent

For anything touching Production widely, build the reverse change set before you deploy. You'll be very glad of it roughly once a year.

Error decoder

Paste a fragment of the error, or describe the symptom. Deployment errors are written for the platform, not for you — most map to something quite simple.

The target org isn't in the dropdown when I try to upload
What it means

Inbound changes aren't authorised in the target org. Authorisation is granted by the receiver.

Fix

In the target: Setup → Deployment Settings → Edit the connection → tick Allow Inbound Changes → Save.

This change set is closed / cannot be edited
What it means

Expected behaviour. Uploading freezes a change set permanently.

Fix

Clone it, make your change, bump the version in the name, upload again.

In field: field — no CustomField named X found
What it means

Something in the set references a field that isn't in the set and doesn't exist in the target.

Fix

Add the field, re-run dependencies, clone and re-upload.

Field X must be included in the page layout (or other required-field errors)
What it means

A field marked required at field level arrived without a layout that displays it.

Fix

Add the page layout to the set — or reconsider whether the field needs to be required at field level rather than enforced by a validation rule.

An object of type Layout was named in layout assignment, but was not found
What it means

The layout, or the record type the assignment depends on, is missing from the set.

Fix

Add both the layout and the record type, then re-run dependencies.

Not available for deploy for this organization
What it means

The target org doesn't have that feature enabled, or the edition differs.

Fix

Enable the feature in the target first, as a pre-deployment manual step, then deploy. This is exactly the kind of thing that belongs on the pre-deployment list.

Average test coverage across all Apex classes is XX%, at least 75% is required
What it means

Org-wide Apex coverage is below the Production threshold. Nothing about your change set is wrong — the org doesn't meet the bar.

Fix

Developer work in the source org: writing or extending tests. This is not solvable on release night. Catch it by validating days ahead.

Test coverage of selected Apex trigger is 0%
What it means

Every trigger needs some coverage of its own, independent of the org-wide figure.

Fix

A test that exercises the trigger. Again — developer work, done ahead of time.

Another deployment is already in progress
What it means

One deployment at a time per org.

Fix

Check Setup → Deployment Status and wait for the running job. Don't cancel someone else's deployment without asking them.

Insufficient access rights on cross-reference id
What it means

Something references a record, user, or owner that doesn't exist in the target org.

Fix

Usually a dashboard running user, a queue member, or a folder owner. Create or remap it in the target.

Duplicate value found: field duplicates value on record
What it means

A component with that API name already exists in the target, or a uniqueness constraint conflicts.

Fix

Compare against the target org before re-uploading. Watch for a component created directly in the target by someone else.

Entity is not org-accessible / Entity 'X' not found
What it means

The object or feature a component depends on is missing or not enabled in the target.

Fix

Enable or create the dependency in the target first.

The Quick Deploy button has disappeared
What it means

The validation expired, relevant metadata changed, or another deployment ran in between.

Fix

Re-validate. Nothing is broken — this is the platform refusing to trust a stale result.

It deployed successfully, but users can't see the change
What it means

The most common outcome of a "successful" deployment. The metadata arrived; visibility didn't.

Work down this list in order
  1. Field-level security wasn't deployed, or the profile wasn't in the set
  2. The field isn't on the page layout the user actually sees
  3. A permission set was deployed but never assigned to anyone
  4. A record type isn't assigned to their profile
  5. A flow arrived inactive
  6. A custom setting is empty in the target
The automation ran twice / the old version is still firing
What it means

Activating a new flow version doesn't necessarily deactivate the previous one, and an old rule may still be active alongside the new one.

Fix

Check which versions are active on the object. Deactivate the superseded version. This belongs on the post-deployment list so it never becomes a surprise.

I need to remove a field from Production and the change set won't do it
What it means

Change sets add and update only. Deletion is not a capability they have.

Fix

Delete it manually in the target, or use a destructive-changes deployment through the Metadata API. Either way it's a deliberate, recorded step — not something to do quietly.

Governance and safety rails

Mechanics keep a deployment correct. These keep it survivable.

Who can deploy to Production

Keep the list short and named; everyone else requests. The person who built the change set shouldn't be its only reviewer, and ideally isn't the person who approves it. Deploying needs the Deploy Change Sets permission in the target org — grant it deliberately rather than by accident.

Deployment windows

  • Good: early-to-mid week, outside business hours, with the deployer available afterwards.
  • Bad: Friday afternoon. Month-end and quarter-end in sales-heavy orgs. The day before a holiday. Any time nobody who understands the change is reachable.
  • Freeze periods: agree in advance when nothing ships — quarter-end close, major campaigns, the week a Salesforce seasonal release lands in your org.
The shape that works

Validation during business hours gets you help. Deployment out of hours gets you safety. Do both.

Test levels and rollback, decided in advance

  • Run local tests is the default choice for Production. Reach for Run all tests only when a managed package is genuinely implicated.
  • Validate far enough ahead that a coverage failure is an inconvenience rather than a cancelled release.
  • Rollback is not a feature. For anything touching Production widely, build the reverse change set before you deploy. For automation, know which switch you'd flip to stop the harm.
  • Write down what "we abandon this" looks like before you're in it — usually a time limit rather than a diagnosis.

Go / no-go — nothing ships to Production until all are true

Keep a release log

One row per deployment: date, change set name and version, ticket, who deployed, who approved, manual steps completed, outcome.

When something breaks three weeks later, this is the first thing you'll want — and the last thing you'll have if you never started it.

The seven stages

  1. Connect — in the target, allow inbound from the source. One-directional.
  2. Create — versioned name, real description.
  3. Add — one type at a time. Profiles last.
  4. Dependencies — add what you need, exclude what would overwrite, re-run after changes.
  5. Manual steps — two written lists, before and after.
  6. Upload and validate — upload freezes it. Always validate.
  7. Deploy and verify — pre-steps, deploy, post-steps, smoke test as a real user, log it.

Golden rules

  1. Change sets add and update only. Never delete.
  2. The receiving org authorises inbound.
  3. Uploading freezes the set. Clone to change it.
  4. Add profiles last — they only carry settings for components in the set.
  5. Validate first, every time, into Production.
  6. All-or-nothing — one failure means nothing deployed.
  7. There is no undo. Prepare the reversal before you need it.
  8. Test as a real user, not as an admin.

Never travels in a change set

  • Data of any kind — including custom setting values
  • Deletions
  • Permission set assignments to users
  • Record type assignment to profiles
  • Standard picklist values (usually)
  • Flow activation (usually) — and the old version stays active
  • Queue membership; assignment rule activation
  • Integration secrets, named credentials, scheduled jobs
  • Report, dashboard, and template folders you forgot to include

Go / no-go

  • UAT signed off, by name
  • Validated against the target
  • Manual steps written — before and after
  • Rollback plan decided
  • Window agreed, approver said go
  • Someone who understands the change is around afterwards

Deployed fine, nobody sees it

Check in this order:

  1. Field-level security / profile not in the set
  2. Field not on the layout the user sees
  3. Permission set deployed but not assigned
  4. Record type not assigned to the profile
  5. Flow inactive
  6. Custom setting empty

Deployment path: Dev → UAT / Full → Production. Change sets add and update only; they never delete, and there is no undo.
